# Workflow: Matching Code + Figma Output

The point of generating both is that a designer gets a screen they can keep editing in either surface — Claude Code for the real component code, Figma's canvas for visual/layout tweaks — without the two drifting apart. That only works if both outputs are built from the same tiered components and the same design tokens.

## Producing the code screen

1. Resolve every component to a tier using [component-tiers.md](component-tiers.md) (see SKILL.md Step 2).
2. Use the real Storybook imports/props for each Tier A/B component — pull these from `component-tiers.md`'s per-component notes, or from the Storybook instance directly if notes are incomplete. Never invent a prop, variant, or component that isn't documented.
3. Mark every Tier B component in code with a short comment, e.g. `// Tier B: not yet Code Connect-mapped, verify Figma placement manually`.
4. Pull colors/spacing/typography from [design-tokens.md](design-tokens.md) rather than hardcoding values.

## Producing the Figma frame

In both cases the goal is the same: place a real **instance** of the actual design-system component (linked to its master, so it inherits future updates) — never a redrawn copy. What differs is how the matching Figma node is found:

**Hard constraint — one library only.** This skill's entire tiering system (`component-tiers.md`, `figma-component-index.md`) was built from a single Figma file: **"DS - React"** (fileKey `cMyPhFndkPeXR6UkIuZujT`, library key `lk-d2af2fc51554edff2f4e2f7ee7f4dc19ca61b38adf60d90eb0444ad9315a208bd58b1baa1e2be133aa90ab2733656bea224cd42315a7f33fc19ea4775b6068fa`). **Never place a component from any other library, no matter how relevant its name sounds or how confidently `search_design_system` returns it.** A working Figma file typically has many other libraries enabled — this workspace alone also surfaces "eToros Design System (Desktop only)," "OLD - Inner Pages Design System," "New Marketing Design System," "Screen Components," a "Functional UI Kit" test file, and a community "Untitled UI" kit. None of these are the real eToro design system this skill documents, even when a component in one of them has an almost-identical name (this skill already placed a wrong-library "Top bar - Desktop" from "eToros Design System (Desktop only)" once, instead of the real "Top bar - desktop" in DS - React — the names are nearly identical, which is exactly how this mistake happens). Concretely:
- Always pass `includeLibraryKeys: ["lk-d2af2fc51554edff2f4e2f7ee7f4dc19ca61b38adf60d90eb0444ad9315a208bd58b1baa1e2be133aa90ab2733656bea224cd42315a7f33fc19ea4775b6068fa"]` to every `search_design_system` call for a UI component. Without it, results from every other library are mixed in with no visual distinction beyond a `libraryName` field that's easy to skim past.
- Before trusting any search result, check `libraryName` explicitly reads `"DS - React"` — never assume based on the component name alone.
- Prefer the node IDs already on file in [figma-component-index.md](figma-component-index.md) and [component-tiers.md](component-tiers.md) over a fresh search — they were captured directly from the real DS - React file, so reusing them (get the node's `.key` via `use_figma` against fileKey `cMyPhFndkPeXR6UkIuZujT`, then `importComponentByKeyAsync`) is more reliable than re-searching and hoping the top result is correct.
- The correct "Top bar - desktop" componentKey, confirmed directly from the DS - React file at node `64911:413329`, is `9e5ea214d1f11f0ce744703edb0242822a4bbfdb` — use this one, not whatever a bare `search_design_system` for "top bar desktop" happens to surface first.
- Storybook (`storybook-source/`) is the only other allowed source — for code, never for Figma placement.

1. For **Tier A** components: use `get_code_connect_map` (or the Code Connect-aware path in `get_design_context`) to resolve the exact, verified Figma component key for the code component, then instance it. This mapping was confirmed when the component was published via Code Connect, so no searching or guessing is involved.
2. For **Tier B** components: there's no Code Connect mapping to lean on, so search for the component directly with `search_design_system` — **scoped to the DS - React library only**, per the hard constraint above — (falling back to `get_metadata` on the known DS - React file if a direct search isn't conclusive), then confirm the match with `get_design_context`/`get_screenshot` on the candidate node before instancing it. This is a heuristic name/structure match, not a verified one — it can land on a deprecated duplicate, a stale version, or a similarly-named but different component (including one from an entirely different library, if the search wasn't scoped). That's exactly why a person should double-check the placed instance against the real Storybook component before treating it as final; it's the gap Code Connect would otherwise close.
3. **For Tier C components — still search for and instance the real Figma component (DS - React only). Tier C blocks *code* fabrication, not Figma reuse.** Tier C means "no Storybook implementation," not "no real Figma component" — components like the Left/Right Side Menu, Desktop Dropdown, and Desktop Tooltip are genuinely real, published components in the DS - React library even though nothing in code implements them yet. Before hand-drawing *any* piece of a Figma build — a nav rail, a top bar, a chip, anything — run a library-scoped `search_design_system` for it first. Import it with `figma.importComponentSetByKeyAsync`/`importComponentByKeyAsync` and `createInstance()` — never approximate with shapes, emoji, or placeholder text when a real component is one search away, and never substitute a same-named component from a different library. Treat a hand-drawn stand-in as a last resort only after confirming a DS - React-scoped `search_design_system` genuinely returns nothing for that component.
4. **Never use emoji or generic glyphs as icon stand-ins — same rule as #3, applied to icons specifically.** The fix is usually to search for and instance the *parent* component that already contains the right icon (e.g. the real "Top bar - desktop" component already has the correct search field, "Ask Tori" button, and notification bell built in) rather than sourcing one icon in isolation — a real top-level component composed of real icons beats hand-assembling icons individually. This still means DS - React only — see the hard constraint above.
5. **Set the real background/surface color explicitly, including the correct light/dark mode.** eToro's Figma color variables (e.g. `Surface/Background/Base`) are multi-mode (Light mode / Dark mode) — the real shipped screens use Dark mode, but an imported variable defaults to whatever mode is active in the *current* file, which may resolve to white/light if that file has no dark context set. Don't assume a bound variable "just works": after binding it, call `node.setExplicitVariableModeForCollection(collection, darkModeId)` on the frame to force the correct theme, and verify with a screenshot rather than assuming. **Also don't assume one mode-setting call covers the whole screen** — a component can bind to its own separate variable collection (same mode names, different collection object) that needs its own explicit mode set even though it's visually nested inside a frame that's already set correctly; check each instance's actual bound-variable collection (not just the parent frame's) if part of a screen still renders in the wrong theme after the top-level fix.
6. **Stretch full-width chrome to the actual available width — don't leave it at its imported default size.** A component instance keeps whatever width it had when created/imported (often a "Hug" size baked in from wherever it was last used), which won't automatically match a different screen's actual content width. Concretely: after placing the Top Bar (or any other edge-to-edge chrome — headers, section dividers, footers), `resize()` it to fill the real available width (screen width minus the nav width, e.g. `root.width - topbar.x`) rather than trusting its default size. A real instance of this: the Top Bar was placed at its default 1640px width inside a screen where the actual available width was 1840px, leaving a visible ~200px gap of bare background before the true right edge instead of the top bar spanning edge-to-edge like it does on real screens. Verify with a screenshot that chrome elements actually reach the edges they're supposed to.
7. Use `use_figma` to actually build/update the frame, following the `/figma-use` and `/figma-generate-design` skills' guidance for translating a layout into Figma (load those skills' instructions before calling `use_figma` — they cover the mechanics this file doesn't repeat).
8. Pull the same token values used in code from [design-tokens.md](design-tokens.md) / `get_variable_defs`, so colors and spacing actually match between the two outputs.

## Prototyping

**Known limitations**: Figma MCP support for wiring interactions (transitions, hotspots, overlays) between frames may be partial or absent depending on what's exposed at the time this skill runs. Before promising a prototype:

1. Check `get_figma_skill` / `use_figma`'s current capabilities for prototyping support.
2. If interactions can be created through the tools, do so and confirm the flow (e.g., tap target → destination frame → transition) matches the intended UX flow.
3. If they can't be automated, place the frames correctly and give the designer explicit manual steps (which frames to link, what trigger/transition to use) so they can finish wiring the prototype themselves in Figma. Don't silently skip this — say plainly that it needs a manual step and why.

## Resyncing storybook-source from eToro-Plus

`storybook-source/` in this skill is a **copy**, not a live link — it was originally extracted from a zip export of the real `eToro-Plus` app repo, and drifts further from reality every time that repo gets new commits. If a local clone of `eToro-Plus` is available on disk (e.g. `~/Documents/Github/eToro-Plus`), it's a genuine git checkout of `github.com/eToro/eToro-Plus` and can be used to refresh this copy directly — no manual zip export needed. Do this whenever the user asks to "refresh"/"resync"/"update" the design system source, or when a component lookup fails and you suspect the bundled copy is stale.

**Steps:**
0. **If no local clone exists**, check `gh auth status` — if `gh` is authenticated with access to `github.com/eToro/eToro-Plus`, clone it fresh (`gh repo clone eToro/eToro-Plus <path>`) rather than giving up. This is slower than an incremental pull (a fresh clone pulls the full repo/history) but it's what actually guarantees an always-current source rather than one that depends on a clone happening to already exist on this machine. If `gh` isn't authenticated either, fall back to the bundled `storybook-source/` as-is and say plainly that it may be stale.
1. `cd` into the local `eToro-Plus` clone and run `git status` first. If there are uncommitted local changes, don't discard or stash them — a plain `git pull` (fast-forward) leaves untouched local edits alone as long as the incoming commits don't touch the same files; if git refuses the pull because of a real conflict, stop and tell the user rather than resolving it yourself.
2. `git pull` to bring `main` current.
3. Copy `libs/etoro-ui/` over this skill's `storybook-source/etoro-ui/`, and `.rnstorybook/stories/` over `storybook-source/rnstorybook-stories/` — full replace, not a merge (`rm -rf` the old copy first, then `cp -R`), so deleted/renamed files in the source don't linger as stale leftovers here.
4. Note the resync date in [component-tiers.md](component-tiers.md)'s header. **This does not re-verify any row's tier or Code Connect status** — it only refreshes the underlying source code. Diff the new top-level folders under `src/` (`find storybook-source/etoro-ui/src -maxdepth 1 -type d`) against what's already tiered, and flag any genuinely new category as unverified rather than assuming it's safe to use.
5. Don't copy `node_modules`, `coverage`, `dist`, or `.nx` directories if present — they shouldn't be, but check before a wholesale copy since they'd bloat the skill for no benefit.

## When something doesn't fit this workflow

If a requested screen needs a Tier C component with no substitute, don't force a workaround (e.g., approximating it with an unrelated Tier A component) — that produces a screen that looks done but isn't real. Flag it in the coverage report (SKILL.md Step 6) instead, so the gap is visible and actionable.
